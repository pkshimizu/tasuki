# Tasuki 設計

要件を人が伝えると、役割ごとのエージェントが仕様作成・タスク分解・デザイン・実装・レビューを進めるソフトウェア開発 AI。

## 1. ねらい

前身の conductor は、指揮役のプログラムが決まった段階（テスト → 実装 → CI → レビュー）を順に進め、書式の点検・回数の上限・許可リストに当たると人の対応待ちにしていた。想定していない状況になるたびに止まり、分岐をプログラムに足す必要があった。

Tasuki は次の作りに変える。

- **プログラム（監視スレッド）は事実を集めて伝えるだけ**。次に何をするかは決めない。
- **次に何をするかは司令塔（LLM）が決める**。段階の順番・やり直しの回数・誰に頼むかをプログラムで固定しない。
- プログラムで必ず守ることは、取り返しのつかないものだけに絞る（5 章）。

## 2. 全体の構成

```
人 ──(Discord)──┐                       ┌── 仕様マスター
                 │                       ├── プランナー
GitHub ──────────┼─▶ 監視スレッド ─▶ 司令塔 ─▶ 指示 ─┼── UIデザイナー
                 │      ▲                            ├── プログラマー
エージェントの終了 ┘      └──── 指示の実行 ◀──────────┘── レビュアー
```

- Tasuki は対象リポジトリとは別の CLI。`tasuki start <フォルダ>` で、1 プロセスが 1 リポジトリを担当する。
- 対象リポジトリの `.tasuki/config.yaml` に設定を置く。プロダクトの情報は、対象リポジトリの文書として管理する（6 章）。
- 実行場所は自分の PC。Discord と GitHub へは PC から読みにいくだけで、外から PC への接続口は作らない。

### 2.1 エージェント

| 役           | すること                                                                         | 書き換えられるもの                  |
| ------------ | -------------------------------------------------------------------------------- | ----------------------------------- |
| 司令塔       | 出来事と今の状況を見て、誰に何を指示するかを決める                               | なし（読むだけ）                    |
| 仕様マスター | 要件を確かめ、不明点を質問し、仕様を書いて PR を作る                             | 作業フォルダ                        |
| プランナー   | 仕様の追加・更新を受けて今の Issue を確かめ、必要な Issue を作成・更新する       | Issue（ファイルは読むだけ）         |
| UIデザイナー | 仕様に UI が要るとき、デザインシステムに沿って HTML モックを作り、PR を作る      | 作業フォルダ                        |
| プログラマー | 指示書（Issue）に従って実装とテストコードを書き、PR を作る。レビューの指摘を直す | 作業フォルダ                        |
| レビュアー   | PR を確かめ、指摘があれば PR にコメントする                                      | PR のコメント（ファイルは読むだけ） |

- プロダクトの情報（6 章）のうち、役に必要な種類を指示に埋め込む。
- どのエージェントも Claude Agent SDK で起動する。認証はこの PC の Claude Code のログインをそのまま使う。
- 毎回新しいセッションで起動する。続きに必要なことは、司令塔が指示書に書いて渡す。
- 結果は決まった形（構造化出力）で受け取る。

```
status   : done（終えた）／question（人に確かめたい）／failed（進められない）
summary  : やったこと・判断の要約
questions: 人への質問の一覧（status が question のとき）
pr       : 作成・更新・レビューした PR の番号（あれば）
verdict  : レビュアーの判定（approve／request_changes）
findings : レビュアーの新しい指摘（重要度・場所・問題・直し方）
resolutions: レビュアーが返す、これまでの指摘の解消判定
responses: 直す役が返す、指摘の番号ごとの対応（直した／直さない／持ち越す）
rule_proposals: ルールの文書に足すとよい決まりの提案（レビュアー）
```

### 2.2 監視スレッド

設定した間隔（既定 60 秒）で次を繰り返す。

1. **集める**: Discord と GitHub を確かめ、前回から変わったことを「出来事」として記録する。
2. **判断を頼む**: 新しい出来事があれば、今の状況と合わせて司令塔に渡す。
3. **実行する**: 司令塔が返した指示を実行する（エージェントの起動・質問の投稿・お知らせ・マージ）。

エージェントは裏で動き、終わると「エージェントの終了」という出来事になって次の判断に回る。

### 2.3 出来事

| 出来事               | もと                                              |
| -------------------- | ------------------------------------------------- |
| 新しい要件           | Discord の要件チャンネルへの投稿                  |
| 質問への返信         | Discord の質問スレッドへの返信                    |
| 仕様・デザインの変更 | main で仕様・デザインの置き場のファイルが変わった |
| Issue の変化         | 作成・更新・クローズ                              |
| PR の変化            | 作成・更新・マージ・クローズ                      |
| CI の結果            | PR の CI が合格・失敗に変わった                   |
| レビューコメント     | PR への新しいコメント（人・レビュアー）           |
| エージェントの終了   | 結果（終えた／質問／進められない／エラー）        |
| 途中で止まった実行   | 再起動したときに、前回動いていた実行              |
| 利用上限からの回復   | 利用上限で止めていた起動を再開できる              |

出来事には重複を防ぐキーを付け、同じことを二度記録しない。

### 2.4 司令塔への入力と出力

入力

- 新しい出来事の一覧
- 今の状況: 進行中の要件、答えを待っている質問、開いている Issue、開いている PR（CI・レビュー・マージ可否）、動いているエージェント
- 最近の判断の履歴（何を指示し、どうなったか）
- マージの設定

出力（指示の一覧と理由）

| 指示                   | 中身                                                                |
| ---------------------- | ------------------------------------------------------------------- |
| `run_agent`            | 役、対象（要件・Issue・PR）、指示書                                 |
| `ask_human`            | 題名、質問、対象。質問チャンネルにスレッドを作る                    |
| `notify`               | お知らせチャンネルに書く文                                          |
| `merge_pr`             | PR 番号。プログラムの門番（5 章）を通ればマージする                 |
| `complete_requirement` | 要件の ID、完了の知らせ。要件を完了にして、お知らせチャンネルに書く |
| `wait`                 | 今は何もしない（理由だけ記録する）                                  |

司令塔はリポジトリと GitHub を読んで確かめることができる。同じ失敗が続いているときにやり方を変えるか、人に質問するかも司令塔が決める。

## 3. 開発の進め方

どの流れも「監視スレッドが出来事を伝え、司令塔が指示を決め、監視スレッドがエージェントを起動する」の繰り返しで進む。下は標準の流れで、司令塔は状況に応じて変えてよい。

### 3.1 要件 → 仕様

1. 人が要件チャンネルに要件を投稿する。
2. 司令塔が仕様マスターへの仕様作成指示を作る。
3. 仕様マスターが仕様を書く。不明点があればそこで止まり、質問を返す。
4. 監視スレッドが質問チャンネルにスレッドを作って質問を書く。人がスレッドに返信する。
5. 司令塔が返信を確かめ、改めて仕様マスターへの指示を作る。3〜5 を仕様が要件を満たすまで繰り返す。
6. 仕様は対象リポジトリで管理し、PR を作ってマージする。

### 3.2 仕様 → Issue → デザイン・実装

1. 仕様やデザインが main で追加・更新されると、司令塔がプランナーに指示する。
2. プランナーは今の Issue の様子を確かめ、必要に応じて Issue を作成・更新する。
3. 監視スレッドが Issue の様子を定期的に確かめ、司令塔に伝える。
4. 司令塔は、進められる Issue があれば指示書を作る。デザインが要れば UIデザイナーに、実装はプログラマーに渡す。
5. UIデザイナーはデザイン（HTML モック）を、プログラマーは実装とテストコードを作り、PR を作る。
6. 進められなくなったエージェントは質問を返し、監視スレッドが質問チャンネルにスレッドを作る。

### 3.3 PR → レビュー → マージ

1. PR が作成・更新されると、司令塔がレビューの要否を決め、レビュアーへの依頼を作る。
2. レビュアーは PR を確かめ、指摘があれば PR にコメントして結果を返す。
3. 司令塔は指摘を確かめ、修正が要ればプログラマー（仕様なら仕様マスター、デザインなら UIデザイナー）への指示を作る。
   指摘と修正の往復を少ない周回で収束させるために、監視スレッドがレビューを PR ごとに記録し、次の役に渡す。

- 指摘には重要度（blocker / major / minor / nit）を付け、PR の中の通し番号を振る。blocker / major が片付いていなければ request_changes、minor / nit だけなら approve。
- 直す役には、番号つきの指摘の一覧を指示書に添える。直す役は、指摘された箇所だけを最小の差分で直し、番号ごとに対応（直した／直さない／持ち越す）を返す。設計の変更が要るものは、その PR では直さず別の Issue に持ち越す。
- 2 回目以降のレビューでは、前回レビューしたコミットと、指摘ごとの対応を指示書に添える。レビュアーは前回からの差分だけを見て、指摘ごとの解消判定と、修正が生んだ新しい blocker だけを返す。
- 司令塔には、PR ごとのレビューの回数・最後の判定・片付いていない指摘の数・レビューしたコミットが今の先頭と同じかを渡す。回数の上限は決めない。往復が続くときにやり方を変えるかは司令塔が判断する。
- レビュアーが、繰り返しそうな指摘をルールの文書に足す提案として返したら、司令塔が文書の更新を指示できる。

4. マージできると司令塔が判断したら `merge_pr` を出す。設定が `auto` ならプログラムがマージし、`human` なら人のマージを待つ。
5. PR を作成したとき・マージされたときは、お知らせチャンネルに書く。

## 4. 並行と作業フォルダ

- 司令塔の判断は 1 回ずつ順に行う。
- 作業エージェントは `limits.agents`（既定 2）まで同時に動かす。
- ファイルを書くエージェントは、対象ごとの git worktree（`~/.tasuki/worktrees/<owner>__<repo>/<対象>`）で動かす。
- `workspace.setup` の準備コマンドは、作業フォルダごとに、初めて用意したときと `workspace.setup_on_change` のファイルが変わったときに実行する。読むだけの役の作業フォルダでも実行する。失敗しても止めず、失敗した内容をエージェントに伝える。
- 確認のたびに作業フォルダを見直し、対象が終わったもの（閉じた Issue・開いていない PR・完了した要件）を消す。エージェントが動いているフォルダ、開いている PR のブランチを取り出しているフォルダ、コミットしていない変更が残っているフォルダは消さない。
- 同じリポジトリを担当する Tasuki は 1 つだけ動かす。起動時にロックを取り、既に動いていれば起動しない。
- 同じ対象（同じ要件・Issue・PR）のエージェントを同時に 2 つ動かさない。重なった指示は、先の実行が終わったあとの判断に回す。

## 5. プログラムで必ず守ること

司令塔やエージェントの判断に任せないのは次の 3 つだけ。

1. **CI 合格がマージの条件**: Tasuki がマージするのは、設定が `auto` で、PR の CI がすべて合格しているときだけ（CI がまだ無い・実行中のときもマージしない）。レビューした PR は、最後の判定が approve で、approve されたコミットが今の先頭と同じときだけマージする（approve のあとに足されたコミットを、レビューなしで取り込まない）。レビューしていない PR は、ここでは止めない（レビューするかは司令塔が決める）。そうでなければマージせず、その事実を司令塔に伝える。
2. **許可した人の投稿だけ読む**: Discord は設定したチャンネルと、許可したユーザーの投稿だけを司令塔に渡す。
3. **危険な操作の拒否**: エージェントの操作は広く許可し、次だけを実行時に拒否する。
   - 既定のブランチへの直接 push、force push、リモートのブランチ削除
   - 作業フォルダの外への書き込み
   - `.tasuki/` の書き換え
   - PR のマージ（マージは 1 の門番だけが行う）

拒否は理由つきでエージェントに返す。エージェントは別のやり方で続けるか、質問を返す。人の許可待ちにはしない。

## 6. プロダクトの情報

開発対象のプロダクトの背景・アーキテクチャ・各種のルールは、対象リポジトリの文書として管理し、必要なエージェントの指示に本文を埋め込む。

| 種類             | 渡す先                                   |
| ---------------- | ---------------------------------------- |
| コンテキスト     | すべてのエージェント（司令塔を含む）     |
| アーキテクチャ   | すべてのエージェント（司令塔を含む）     |
| 仕様作成ルール   | 仕様マスター                             |
| 実装ルール       | プログラマー                             |
| レビュー観点     | レビュアー                               |
| コミットルール   | 仕様マスター・UIデザイナー・プログラマー |
| タスク作成ルール | プランナー                               |
| プルリクルール   | 仕様マスター・UIデザイナー・プログラマー |
| マージルール     | 司令塔                                   |

- 置き場は設定の `knowledge` で種類ごとに決める（既定値あり）。ファイル・フォルダ・その一覧を書ける。無い文書は読み飛ばす。
- エージェントを起動するたびに、既定のブランチの最新の内容を読む。作業中のブランチの内容は読まない（ルールを書き換える PR は、マージされてから効く）。
- 役ごとの追加の指示（`.tasuki/<役>/*.md`）は持たない。司令塔への進め方の方針は、コンテキストに書く。

## 7. 利用上限

- Agent SDK の利用上限の知らせを受けたら、回復時刻まで新しいエージェントを起動しない。
- 上限で終わった実行は、回復したあと司令塔に伝え、やり直すかを決めさせる。

## 8. 設定

対象リポジトリの `.tasuki/config.yaml`

```yaml
github:
  repo: owner/name
discord:
  channels:
    requirements: "..." # 要件チャンネル
    questions: "..." # 質問チャンネル
    notices: "..." # お知らせチャンネル
  allowed_users: # 許可する人（ユーザー ID）
    - "..."
merge: # 工程ごとに auto（自動）か human（人のレビュー後）
  spec: human
  design: human
  implementation: human
  require_ci: true # CI の無いリポジトリで自動マージを使うときだけ false
poll_interval: 60 # 確認の間隔（秒）
limits:
  agents: 2 # 同時に動かす作業エージェントの数
language: 日本語 # エージェントが書く文章の言語
paths:
  specs: docs/specs
  design: docs/design
  design_system: docs/design-system
workspace: # 作業フォルダの準備（省略可）
  setup: # 作業フォルダを用意したあとに Tasuki が実行するコマンド
    - npm ci
  setup_on_change: # このファイルが変わったら、もう一度実行する
    - package-lock.json
admin: # 管理画面（省略可）
  enabled: true
  port: 4680
agents: # 役ごとの設定（省略可）
  programmer:
    model: ...
```

- Discord のトークンは環境変数 `TASUKI_DISCORD_TOKEN` で渡す。
- 役の名前（`agents.<役>` に使う）: `dispatcher`・`spec-master`・`planner`・`designer`・`programmer`・`reviewer`
- `knowledge` で、プロダクトの情報の置き場を種類ごとに変えられる（6 章）。
- PR がどの工程（仕様・デザイン・実装）かは、変えたファイルの置き場で決める。仕様の置き場だけなら仕様、デザインの置き場だけならデザイン、それ以外は実装。

## 9. 記録

`~/.tasuki/state/<owner>__<repo>.db`（SQLite）に置く。

- 出来事（処理済みかどうか）
- 読んだ位置（チャンネル・スレッドごと）
- 要件（投稿 ID・本文・状態）
- 質問スレッド（スレッド ID・対象・出どころの役・答えたかどうか）
- エージェントの実行（役・対象・指示書・結果・開始と終了）
- 司令塔の判断（入力の要約・指示・理由）
- PR の様子（番号・タイトル・ブランチ・工程・状態）。閉じたあとも管理画面に出すため
- エージェントの実行ごとの、どの要件のための実行か（司令塔が指示に添える）。管理画面で、要件ごとに Issue・PR・経過を追うため。判断には使わない
- レビュー（PR・回・レビューしたコミット・判定）と指摘（番号・重要度・場所・問題・直し方・対応の状態）
- PR と Issue の前回の様子（変化を見つけるため）

段階や回数は記録しない。今の状況は毎回 GitHub と Discord から読み、記録は「何が新しいか」と「何をしたか」を覚えるために使う。

## 10. 管理画面

`tasuki start` と同じプロセスから配信する（`src/admin/`・`web/`）。デザインは `docs/design/admin/`。

- この PC からだけ開ける（127.0.0.1 で待ち受け、ほかの名前で届いた要求は断る）。ログインは無い。
- ポートは決まった番号（既定 4680、`admin.port`）。使用中なら空いているポートに切り替える。
- 画面は React ＋ Vite で作り、ビルドしたものを配布物に含める。
- 内容は `/api/...` が JSON で返す。記録（SQLite）と、監視スレッド・指示の実行の今の様子から組み立てる。
- 変化は `/api/events`（Server-Sent Events）で知らせる。何が変わったかは伝えず、画面は知らせを受けたら今見ている内容を読み直す。
- 段階の表示は持たない。進み具合は、出来事・司令塔の判断・エージェントの実行の時系列で見せる。
- 操作は `POST /api/ops/...` で受ける（止める・起動し直す・エージェントを 1 つ中断する）。管理画面そのものからの要求だけを受け付ける: 管理画面が付ける印のヘッダーがあり、要求の出どころ（Origin）がこの管理画面と同じであること。ほかのサイトのページからは、どちらも満たせない。
  - 止める・起動し直すは、新しい指示を出すのをやめて、動いているエージェントの終了を待つ（Ctrl+C と同じ）。起動し直すときは、同じプロセスのまま、設定の読み込みからやり直す。
  - 中断は、そのエージェントの実行だけを止め、「途中で終わった」出来事として司令塔に渡す。作業フォルダは片付けない。次にどうするかは司令塔が決める。
